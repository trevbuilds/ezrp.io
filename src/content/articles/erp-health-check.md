## Why it matters

Replacement is the most expensive available answer. It is the right answer often enough that it gets chosen before the question has been asked properly.

- **The symptom is rarely the cause**: "The system can't do it" usually means unconfigured, untrained, or a process the system was never told about.
- **A replacement inherits the data**: Bad master data moves across unless it is fixed, and fixing it is business work either way.
- **It sizes the real problem**: Customisation, integration count and support model tell you what any replacement is actually up against.

## The workflow

```steps
Scope :: Which systems, processes and sites are in the assessment.
Functional assessment :: Process by process, what is supported, what is worked around and why.
Data assessment :: Master data quality, duplication, completeness and ownership, measured.
Technical assessment :: Version currency, customisation, integration count and infrastructure.
Cost and support :: Total cost of ownership, support model, and key-person dependency.
Risk :: Security, continuity, compliance and end-of-support exposure.
Findings :: Options — fix, upgrade or replace — with cost and time for each.
```

> Count the spreadsheets. The number of spreadsheets between two systems is the single most reliable indicator of where the estate is actually failing, and it is easier to count than to argue about.

## What you need in place

- **Access to the people who do the work**: Not just to the people who own the systems.
- **Measured data quality**: Duplicate rates and completeness, sampled, not estimated.
- **A customisation inventory**: With reasons where they are still known.
- **An interface catalogue**: Including the undocumented ones.
- **Real total cost of ownership**: Licence, support, infrastructure and internal effort.
- **Three options costed**: Fix, upgrade, replace — so replacement is chosen, not defaulted to.

## Questions to ask

```qa
Workarounds :: Where does work leave the system and come back? :: Each one is a requirement nobody wrote down.
Data :: What is our duplicate rate on customer and supplier master? :: Measure it; the estimate is always lower.
Customisation :: How much, and does anyone know why? :: Unexplained customisation is the upgrade blocker.
Support :: How many people can support this, and what is the bus factor? :: Key-person dependency is a risk that reads as stability.
Cost :: What does this actually cost per year, all in? :: Including internal effort, which is rarely counted.
Fixability :: Which complaints could be fixed without replacement? :: Usually more than expected.
```

## Metrics and KPIs to track

```metrics
Process coverage :: Processes fully supported against worked around.
Master data quality :: Duplicate and completeness rates by domain.
Customisation count :: By type, and share blocking upgrade.
Interface count :: Documented against discovered.
Total cost of ownership :: Per year, all components.
Support concentration :: Systems with a single capable supporter.
```
